# Internationalization

Text domain: **`aggressive-ads`**. Catalogs in `languages/`.

Every user-facing string is translatable — forms, validation messages, statuses, notifications, emails, admin screens, accessibility labels, and error text. A hard-coded string in an error path is the one a translator never sees, because nobody demos the failure case.

## The plugin `.mo` naming trap

**Plugins and themes name compiled catalogs differently, and porting the theme's script here breaks translation silently.**

The LAAO theme's `bin/i18n/compile.sh` renames `laao-<locale>.mo` → `<locale>.mo`. That is correct *for a theme whose domain path is inside its own directory*, because `_load_textdomain_just_in_time()` special-cases the template and stylesheet directories and looks for the unprefixed name.

**A plugin is not that case.** `load_plugin_textdomain()` and the JIT loader both look for `aggressive-ads-<locale>.mo`. Renaming produces a file WordPress will never find, and the failure mode is that the site simply renders English — no error, no warning, nothing in the log.

So: `compile.sh` here keeps the prefixed name. **The rename step is deleted, not ported.** This paragraph exists because the theme's script is otherwise an excellent thing to copy, and the one line that must change is the one that looks most like boilerplate.

## The second silent failure: registering the directory

The naming trap above is only half of it, and this half was live in this plugin
until the catalogs were set up.

**Just-in-time loading never searches a plugin's own folder.**
`WP_Textdomain_Registry::get_paths_for_domain()` returns exactly three
locations: `WP_LANG_DIR/plugins`, `WP_LANG_DIR/themes`, and a custom path that
is only ever populated by `load_plugin_textdomain()` or
`load_theme_textdomain()`. This plugin called neither. It shipped `Domain Path:
/languages` in its header, which is metadata for translate.wordpress.org and
nothing else at runtime.

So every catalog placed in `languages/` would have been ignored, and a site
would have been translated only if somebody had installed a language pack into
`wp-content/languages/plugins/`. `Plugin::load_translations()` now makes the
call, on `init` — earlier is a `_doing_it_wrong` notice since WordPress 6.7,
because the locale is not settled until then.

**Both failures are invisible from every signal except the rendered string.**
`load_plugin_textdomain()` returns `true` whether or not it found a catalog.
The POT can be current, the `.po` valid, the `.mo` compiled and the placeholders
perfect while the whole site renders English.

`tests/php/Integration/TranslationLoadingTest.php` therefore asserts on `__()`
output. It writes a small binary `.mo` by hand rather than shelling out to
`msgfmt`, because this suite runs with `failOnSkipped` and a test that skips
where gettext is missing is a test that stops running exactly where nobody is
watching. Deleting the `load_plugin_textdomain()` call fails it; renaming to the
theme's unprefixed convention fails it too.

One constraint that shaped it: WordPress caches loaded catalogs per request in
`WP_Translation_Controller`, and `WP_UnitTestCase` does not reset that. Each
test uses its own locale, and the fallback-to-English assertion lives inside the
first test rather than in a third one, because a third load of the same domain
in one process does not take.

## Machine translation

`pnpm i18n:translate` fills empty and fuzzy entries through **a model you host
yourself** — any OpenAI-compatible `/v1/chat/completions` server (LM Studio,
Ollama, llama.cpp). Its address and model id live in `.env.local`
(`I18N_LOCAL_URL`, `I18N_LOCAL_MODEL`); `.env.example` documents the rest.
Temperature is always 0.

Every filled entry is flagged `aggr-mt` with a comment naming the engine, and
translation never runs in `build` or in the release job. **CI cannot reach a
model on somebody's machine**, so translating is a deliberate local act rather
than something a runner does on a push.

**The hosted engines were removed on 2026-09-11**, and what they cost is the
argument for how this works now. DeepL's quota was exhausted for as long as
anyone looked, so every string silently fell through to MyMemory, a
translation-memory aggregator. Two runs — 718 strings — went out that way with
no signal but a `via` tag inside a PO comment. Reviewing one of those drafts
found roughly a third of it defective: an ad creative rendered as a shopping
cart (*Warenkorb*), screen widths as sieve widths (*Siebbreiten*), creatives as
creative people (*Kreative*), and a string that switched from *Sie* to *du*. It
was closed rather than merged. A local model takes instructions an MT engine
cannot, which is what fixed those: the product, the register, the domain sense
of words English overloads.

### The run only asks for what it does not have

Empty and fuzzy entries only. A clean translation is never re-sent and comes
back byte-identical; a second run with nothing to do asks for nothing and does
not rewrite the catalog. `msgmerge` supplies the rest of the contract: new
strings arrive empty, changed sources arrive fuzzy, and a string deleted from
the source is commented out rather than dropped.

**Obsolete entries are kept verbatim.** `parsePo()` used to discard them —
every line of a `#~` block begins with `#` and none parses as a msgid — so the
next write deleted the translation of any string the source had lost. That is
the opposite of why `msgmerge` keeps them: restoring a reverted string should
not cost its German. They are never re-parsed, never offered to the model, and
skipped by the lint.

### Placeholders, echoes and what a refusal means

`placeholdersIntact()` in `po.mjs` is the single definition of the rule, and it
compares **both directions**. A translation that invents a placeholder is as
broken as one that drops it: a model answering from a translation memory
returned "All campaigns" as German carrying a `%d` borrowed from a neighbouring
"%d campaigns", and `%d` in a string PHP passes no argument to is a broken page.
The lint calls that function rather than restating it, and a test asserts the
two agree over a table of cases.

An **echo** — the model returning the source unchanged — is refused, not filed.
Some strings really are identical in both languages ("Euro", "Code", "CTR"), and
nothing mechanical separates those from a model giving up; a person can, and is
asked. An **empty answer** is refused the same way.

A refused string is left empty, named on stdout, emitted as a `::warning::`
annotation under GitHub Actions, and subtracted from what `judgeRun()` calls
unfinished. It does not stop the locale — but a string nothing *tried* to
translate still fails the run.

As a backstop, any machine-written entry whose placeholders do not match is
demoted to fuzzy just before the file is written, so a run cannot produce a
catalog its own validation would reject. Human translations are never swept: a
broken one fails the lint loudly, because quietly flagging somebody's work hides
a problem only they can fix.

### A fuzzy flag is a review state, and only the run that fills an entry clears it

`serializeEntry()` once cleared `fuzzy` and stamped `aggr-mt` on every entry it
wrote — the whole catalog, not the handful a run translated. `msgmerge` had
fuzzy-matched a newly added "…cannot be used: `%s`" onto the older translation
of the same sentence without the `%s`, correctly marking it fuzzy; the next
write silently un-marked it, the lint stopped skipping it, and the job failed on
a placeholder the machine had never touched. The same line relabelled reviewed
human translations as machine output. Flags are now written exactly as they
stand.

### The prompt carries what an engine could not be told

`LOCAL_TERMS` and `LOCAL_REGISTER` in `providers.mjs` give the model the
product, the formal register (German *Sie*, never *du*), the placeholder tokens,
and the domain sense of overloaded words. Each string's `msgctxt` and translator
note go in the system prompt, so the user message is the text and nothing the
model might echo back. `LOCALE_GLOSSARY` still runs afterwards as a substring
backstop: the prompt is the instruction, the glossary is the correction.

The German terms are **proposals reviewed by product**, not settled German.
*Werbebuchung* (line item) and *Platzierung* are the terms Google Ad Manager's
German interface uses. Two came out of review: *delivery* and *fill* were one
blanket rule and are now separate concepts, because what is delivered is the ad
while a request is served or processed; and "worth reporting" gained a rule
after the first gate rendered it *meldepflichtig*, the legal term for a
mandatory report.

**Only German has a term list.** Spanish, French and Italian have a register
rule and nothing else, so each needs its own reviewed terminology before its
catalog is worth running.

### A model on your machine gets restarted

The first full German run stopped after 567 of 1,386 strings: the model was
reloaded mid-run, the server answered `HTTP 400` until it was back, and one 400
was read as the provider refusing for good.

A failed request is retried with backoff for about two minutes, which outlasts a
reload. Only 401, 403 and 404 stop at once — waiting cannot supply a missing
model. When the retries are exhausted the server is asked whether it is healthy:
still serving the model means the request was that string's problem and only
that string is skipped; not serving means the run stops so a re-run can resume,
rather than spending two minutes on every string left.

Classification is by explicit code (`MT_RETRYABLE`, `MT_PROVIDER_STOP`), checked
before anything reads a message, so a status inside a message can no longer
decide the fate of a locale. The server's own reason is kept in the error, up to
300 characters, because that first 400 could not be diagnosed at all — its body
went unread.

**If the model is not running, the run says so in red and writes nothing.** A
second, distinct red message covers the model stopping partway through, where
the finished work is kept and only the claim is withdrawn. Colour honours
`NO_COLOR` and `FORCE_COLOR`.

### The quality gate

Measured twice against the same 21-string spread sample, scored under a rubric
fixed before any output was seen — defective means a wrong domain meaning, the
wrong register, a broken placeholder, or ungrammatical German.

| | defective of 21 |
|---|---|
| MyMemory | 8 |
| Qwen 3.8 27B, first prompt | 3 |

Three is not two, so the gate was **not** declared met on that sample. The
prompt changes it prompted were made *after* seeing those strings, and
re-scoring the same 21 would have graded the prompt against its own answer key.
A fresh 21 were drawn by a fixed rule — a stride over the POT, excluding the
first set, zero overlap — before the revised prompt ran against them, with the
rubric written down first, including that a refused string writes nothing and so
is not a defect, but more than two refusals fails.

| | result | gate |
|---|---|---|
| Defective | 1 / 21 | ≤ 2 |
| Refused | 1 | ≤ 2 |
| Howlers | none | none |

**Passed.** The defect was a plural — "Last %d day" became *Letzte %d Tage* in
both forms, so the singular reads "Letzte 1 Tage". The refusal was "Status",
correct German, left for a person to confirm. Two patterns for a native review
of a full catalog: the singular form of `%d` plurals, and a mismatched closing
quote after „.

One defect in the first gate was **not the model's**: seven conversion-refusal
reasons were predicate fragments inserted into `'%1$s %2$s'`, so the English read
"5 named a conversion belonging to another advertiser". German needs the verb to
agree with the number, and a fragment carrying the verb inside a template that
cannot reorder it is untranslatable in isolation — by a model or a person. Each
reason is now one `_n()` sentence with the count inside it, and
`ConversionHealthTest` enumerates `Conversion_Attribution`'s reasons by
reflection, so a new one added without a sentence fails rather than disappearing
from the screen.

About 4 seconds a string on that hardware: a full German catalog of ~1,386
strings is roughly an hour and a half.

### Where the two halves live

`providers.mjs` is talking to the model: the prompt, placeholder and brand
protection, the glossary, refusals, retries and the health check.
`translate.mjs` is walking a catalog and writing it back. The seam is not
arbitrary — the provider half changed four times in two days while the catalog
walk did not change once.

## The drift gate

`bin/i18n/check.sh` regenerates the POT, normalizes both copies by stripping volatile headers (`POT-Creation-Date`, `PO-Revision-Date`, `Project-Id-Version`, `X-Generator`), and diffs. A new translatable string committed without regenerating the POT fails CI with the diff attached.

Normalization matters: without it, every run differs by a timestamp and the gate is useless noise that gets disabled within a week.

The regenerated copy is written to `languages/.drift.pot` and removed by a trap, rather than to `/tmp`. That is not fussiness about tidiness — it keeps the file inside the repository, which is the only place every possible extractor can reach.

## The extractor is pinned, and that is the point

`bin/ci/install-wp-cli.sh` fetches a **pinned, SHA-256-verified WP-CLI phar** into `.cache/ci/wp`, and `aggr_i18n_wp()` prefers it over whatever `wp` is on `PATH`.

A drift gate compares this machine's extraction against the committed catalog. If the extractor is "whatever WP-CLI happens to be installed", two developers on different releases flag each other's correct commits as drift, forever — and a gate that cries wolf is a gate somebody switches off. Pinning is what makes the comparison mean anything.

The checksum is not decoration either: this downloads an executable and then runs it over the whole source tree in CI. The same reasoning that makes the plugin updater verify its own archive applies here with more force.

`wp i18n make-pot` needs no database and no WordPress install, so the lane does
**not** start Docker. Its explicitly pinned WP-CLI phar keeps extraction fast
and reproducible on the host.

## PO validation is msgfmt, and it never skips

`bin/i18n/validate-po.sh` runs `msgfmt --check` on each catalog.

**A missing `msgfmt` is a hard failure, never a silent skip.** `wp i18n make-mo` is lenient — it reports success on an unterminated `msgid` and on a msgid/msgstr placeholder mismatch alike, which is precisely the defect that reaches a translated production site as a mangled sentence or a fatal `sprintf`. `msgfmt --check` checks formats, headers and domain, and exits non-zero. The sibling theme shipped four dead catalogs for months because its equivalent gate quietly selected the lenient validator whenever the strict tool was absent.

So the CI job installs gettext explicitly rather than hoping the runner image ships it. Skipping the strict check when the tool is missing means the check only ever runs where it was never going to fail.

## Translator comments

Any string containing a placeholder needs a preceding `/* translators: */` comment naming what each placeholder is:

```php
/* translators: 1: uploaded dimensions, e.g. 1200 × 400. 2: required dimensions. */
sprintf( __( 'Uploaded: %1$s. Required: %2$s.', 'aggressive-ads' ), $got, $want )
```

**This is already enforced, and not by a script of ours.** `WordPress.WP.I18n.MissingTranslatorsComment` is part of the WordPress standard PHPCS already runs, and it fails the build on a placeholder string without a comment — verified by deleting one and watching `pnpm lint:php` go red.

An earlier draft of this document specified `bin/i18n/lint-translators.sh`. Writing it would have been a second implementation of a check that already runs, with its own bugs and its own drift. Do not add it.

Without the comment a translator sees `%1$s` and `%2$s` with no way to know which is which, and in a language that reorders the clause they have to guess.

## JavaScript strings, and the script-module gap

**`wp_set_script_translations()` does not work for script modules.** The Script Modules API — which the Interactivity API is built on — has no translation mechanism in WordPress today. This is a core gap, not something we can work around at the call site.

So **every user-facing string in an Interactivity store is hydrated server-side** through `wp_interactivity_state()`, already translated by PHP:

```php
wp_interactivity_state( 'aggr/upload', array(
    'i18n' => array(
        'uploading' => __( 'Uploading…', 'aggressive-ads' ),
        'failed'    => __( 'Upload failed. Try again.', 'aggressive-ads' ),
    ),
) );
```

The store reads `state.i18n.uploading`. No string literals in TypeScript that a user will ever read.

Classic (non-module) scripts still use `wp_set_script_translations()` normally, and `make-json` produces their catalogs. Recorded in [known-issues.md](known-issues.md), which now also carries what removing the hydration would take — core closed the gap in WordPress 7.0, and this plugin's floor is 6.7.

## Release

`.mo` files are **build output**, like `dist/`: gitignored, never committed. `bin/release/package.sh` runs `bin/i18n/compile.sh` before staging, so the archive always carries a compiled catalog for every committed `.po`.

`bin/release/verify-package.sh` then asserts independently that **every `.po` in the ZIP has its `.mo` beside it.** Two mechanisms for one fact, deliberately: forgetting to compile is otherwise invisible — the site just renders English, and the first report comes from a user weeks later.

Until a locale `.po` is committed, both are no-ops. That is the intended state, not an omission: the tooling and the POT ship first so translators have something to work from, and nothing here fabricates a catalog nobody has translated.
